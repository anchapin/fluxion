## Detailed Gap Descriptions

### G1 — Section 8.1 Report Header Information

**Required by ASHRAE 140-2023 Section 8.1:**
> The report shall include the name of the program, version number, program developer, date simulation runs were performed, the edition of ASHRAE 140 being tested against, and identification of the weather data file used.

**Current state:** The compliance report generated by `report.rs` does not include any of these fields.

**Fix:** Add a `ReportHeader` struct to `report.rs` populated with:
- `program_name: "fluxion"`
- `program_version`: from `Cargo.toml` `[package].version`
- `developer`: configurable field
- `run_date`: `SystemTime::now()`
- `ashrae_edition: "ASHRAE 140-2023"`
- `weather_file_id`: from validation config (blocked by #732)

**User-facing documentation:** Once fixed, `docs/ASHRAE140_VALIDATION.md` should include a sample report header showing these fields.

---

### G2 — Energy Units: MWh → kWh

**Required:** ASHRAE 140-2023 standardized on kWh for all energy reporting (prior editions used GJ).

**Current state:** Code reports energy in MWh. All output tables and validation comparisons use MWh. Reference data loaded from `refdata/` must also be confirmed as kWh.

**Fix:** Apply a 1000× factor at the output layer (or fix the internal unit throughout). Confirm `refdata/` reference ranges are kWh, not MWh.

**User-facing impact:** The EUI disclaimer in the README/QUICKSTART should be updated once units are standardized to clarify: output will be in kWh (not the current raw cumulative metric), with appropriate normalization.

---

### G3 — Peak Load Timestamps

**Required by ASHRAE 140-2023 Section 8.2.2:**
> Report the date (month and day) and hour of occurrence for each peak heating and cooling load.

**Current state:** `ValidationResult` struct stores only `fluxion_value: f64` — the peak load magnitude. No timestamp is retained.

**Fix required (Rust):**
- Modify internal simulation to record `(month, day, hour)` when a new peak load is encountered
- Add `peak_timestamp: Option<(u32, u32, u32)>` (month, day, hour) to `ValidationResult`
- Include timestamp in report output

**Documentation output once fixed:** Update `docs/API_REFERENCE.md` to document the new timestamp fields in the Python-facing result object.

---

### G4 — Incident Solar Radiation

**Required by ASHRAE 140-2023 Section 8.2.3:**
> Report annual and peak incident solar radiation on each opaque surface and each window, in kWh/m².

**Current state:** No `IncidentSolar` metric type is defined anywhere in the validator or result types.

**Fix required (Rust):**
- Define `MetricType::IncidentSolar { surface_id: String }`
- Record per-surface solar accumulation during simulation
- Add reporting logic

**Effort note:** This is a medium-complexity physics addition, not just a reporting change. Requires the solar model to track per-surface values.

---

### G5 — Hourly Temperature Profiles for Free-Float Cases

**Required by ASHRAE 140-2023 Section 8.2.4:**
> For unconditioned (free-float) test cases, provide the annual hourly zone temperature profile as tabular or graphical output.

**Free-float cases affected:** 600FF, 650FF, 900FF, 950FF

**Current state:** Validator stores only `MinFreeFloat` and `MaxFreeFloat` (the annual extreme temperatures). The full 8,760-hour profile is not retained.

**Fix required (Rust):**
- Add `hourly_temperatures: Option<Vec<f64>>` (8760 values) to the simulation result for FF cases
- Write these to the report as tabular data (CSV or embedded table)
- Optionally: generate the temperature profile plot via `plotters` (G6)

**Storage note:** 8,760 f64 values = ~70 KB per case. Four cases = ~280 KB of extra data per run. Acceptable.

---

### G6 — Inter-Program Comparison Charts

**Required by ASHRAE 140-2023 Section 8.4:**
> Provide bar charts comparing program results against all reference programs for each metric.

**Current state:** `report.rs` uses the `plotters` crate with stub/placeholder implementations. No real charts are generated.

**Fix effort:** Hard — requires working `plotters` integration and real reference data loaded from `refdata/`. Deprioritized until physics accuracy (DEV-001, DEV-002) is resolved — charts showing incorrect results would be misleading.

**Interim documentation:** `docs/ASHRAE140_VALIDATION.md` can provide manual comparison tables (text) as a stopgap for each Wave as physics fixes land.

## Fix Priority Order

Based on the PM roadmap (physics Waves 1–5 running in parallel):

1. **G2** (units: MWh → kWh) — Low effort, compliance blocker. Fix immediately.
2. **G1** (Section 8.1 header) — Low effort, required for any valid report. Fix immediately.
3. **G3** (peak load timestamps) — Medium effort. Needed once peak load physics (DEV-001) is fixed.
4. **G5** (hourly FF profiles) — Medium effort. Needed for FF case compliance.
5. **G4** (incident solar) — Medium effort. Requires solar physics work.
6. **G6** (comparison charts) — Hard. Defer until physics is correct.
