### Where the engine would consume COP — three candidate sites

- **Option R — site/electric metering (additive).** Convert delivered thermal to input energy at the metering sites: P_input = Q_delivered / COP (heating) and / EER-based or COP (cooling), accumulated next to the thermal counters; new output fields (e.g. annual heating/cooling *electric* kWh), snapshot and CLI surfaces gain the fields. The zone advance never sees COP: temperatures, setpoint satisfaction, clamping, and every existing battery row are untouched by construction. This is the ISO 13790-conformant shape: system energy use lives downstream of the zone need.
- **Option C — capacity re-interpretation.** Read the stored capacity as an electrical input limit and scale delivered thermal by COP at the controller clamp. Premise problem: the repo's capacities are thermal watts with the ASHRAE 140 case semantics (e.g. series_600's heating/cooling capacity rows), and the 140 clamps are wide enough that setpoint misses would move only in contrived configurations. As stated the premise contradicts the standard's meaning of the case inputs; it should be premise-checked against primary sources before any arm is built, and the default expectation is refutation.
- **Option L — recoverable system losses (the fuller fidelity step).** ISO 13790 §10.4.5 defines the internal heat flow rate from recoverable system losses (Φ_int,H / Φ_int,C): auxiliary energy (pump/fan/electronics) plus emission, circulation, distribution, storage and generation dissipation, recoverable into the zone as internal gains. Consuming COP *here* means building the system-loss chain (emitter/distribution/storage) the ideal-loads plant does not have — the largest scope, touching the gains sites themselves, and a genuine fidelity increment for conditioned cases.

### Physics basis — what the sources actually prescribe

- **ISO 13790** (verified from the public final-draft approval text of ISO 13790 hosted at ETH Zürich; quoted as final-draft, not the published standard): the building/zone calculation (the Annex C network this engine implements) computes the energy *need*; system energy use is computed downstream, with scope text naming "generation, storage, distribution, emission and control losses of the space heating and cooling systems". Definitions distinguish recoverable vs recovered system thermal losses ("part of a technical system thermal loss which can be recovered to lower either the energy need for heating or cooling…"; "A system loss can become an internal heat gain for the building if it is recoverable"). §10.4.5.2 (Space heating system): the recoverable-loss gain consists of heat dissipated in the zone from auxiliary energy and from emission/circulation/distribution/storage/**generation**, obtained from the relevant system standard (Annex A), hourly for the simple hourly method, with an explicit national-level simplification to ignore minor recoverable amounts. §10.4.5.3 is the cooling analog. Annex H is "(informative) Accuracy of the method" — the monthly method's "overall system efficiency … including generation" formulation lives in the monthly annex text. The structural fact that matters for this scoping: **generation efficiency (COP for an electric carrier) sits downstream of the zone need; the zone network never depends on it; only recoverable losses re-enter as gains.** Option R is therefore the directly standard-shaped consumption; Option L is the standard's loss-recovery mechanism; Option C has no such anchor.
- **ASHRAE 140** (verification boundary stated honestly): the standard's text is paywalled and its supplemental files sit behind the standing Cloudflare 403 wall, so this doc does NOT quote it. What is verified is this repo's own 140 implementation: the case battery drives heating/cooling by air-temperature setpoints with idealized systems; case specs carry `HVACSystem` COP fields (defaults 3.0/3.2 in `src/validation/ashrae140/mod.rs:149-150`; series_195 variants at 3.2/3.4) that ride along as spec metadata; the validator's metrics are thermal; and the equipment-bearing Cases 800-810 attach `EquipmentSelection::HeatPump` COPs (3.5 / EER 3.0-11.5 with PLR curves) that reach only the topology bridge. The claim "ASHRAE 140 prescribes no equipment-efficiency-sensitive path in this battery" is therefore grounded in the repo's case definitions, validator code, and the standing §LIMIT-44 record — not in the standard's wording. When the wall lifts or the standard's text reaches the repo, this paragraph should be re-anchored against §5-§8 directly.

### Re-record scope

Any default-build consumption is a default-build behavior change: the full battery runs with old→new provenance regardless of option chosen — strict-gate JSON re-record, output-diff CSV, §6/§7 pins, hotloop goldens, grid baseline, contracts — per the standing rule that no engine-side change claims battery-inertness without proving byte-identity of every row by running it. Option R additionally adds output fields, which ride the schema/API/docs surfaces (api/schema.rs, the snapshot bindings, python hvac.py) and their own gates; its expected battery outcome is 42/42 rows at +0.0000% with the new electric fields living outside the thermal CSV. Options C/L change zone behavior and owe the complete re-record with per-case provenance.

### Fidelity-first framing and the honest counterweight

The doctrine (2026-10-22, extended) judges changes as known, verifiable, tested physics — band movement is recorded, never weighted. Option R qualifies on its own merits: the need÷COP conversion is the standard's own system treatment, verifiable by contracts transcribed from the ISO arithmetic (engine literals, not textbook constants), testable red-first, and demonstrable by the measure A/B — SetHVACEfficiency finally moving simulated (input) energy. The counterweight must be stated plainly: **no ASHRAE 140 battery case would move.** All 42 output-diff metrics are thermal delivered energy; the only equipment-bearing rows (800-810) print their Case 600 baseline by construction (§LIMIT-44); the checker cannot adjudicate COP under any of the three options that leave the ideal-loads thermal path intact. The validation story for the eventual PR must say exactly this — correct physics with zero 140 purchase, adjudicated by ISO-derived contracts and the measure-level A/B, with the battery run serving as the byte-identity proof. That is not a weakness in the doctrine: it is the doctrine working as designed (bands are not a decision signal), but the PR prose and the validation doc must carry the statement rather than implying band coverage.

### The r154 tripwire disposition

The `hvac.rs` snapshot pins (read-back returns literal 3.0/3.2) and the python COP-persistence pins exist to make silent advisory drift impossible. When the COP round stores/consumes COP, those pins flip deliberately — dated verdicts, red-first at the tip, re-pinned to the new contract in the same PR — never silently widened or deleted. This is the same discipline the r154 round applied when it first pinned the advisory contract.
