**Batching Architecture:**
- CPU path: Coordinator-Worker pattern with crossbeam channels
- GPU path: SharedBatchInferenceService with dynamic batching
- SessionPool: Provides ONNX sessions with mutex-protected reuse

**Hotspots:**
1. `SessionPool::get_session()` — mutex lock/unlock every inference batch
2. `SharedBatchInferenceService` — builds batches, submits to session, distributes results
3. Channel bottlenecks in CPU coordinator: sending temperatures/receiving loads for 8760 × N steps
4. Batch size tuning: current `max_batch_size = valid_configs.len()` may cause large batches with high latency

**Profiling Plan:**
- Use `perf record -g` on a running batch inference to see time spent in mutexes, session.run, channel ops
- Instrument `predict_loads_batched` with timing logs
- Check if session.run overhead dominates; if so, explore larger batches or session reuse
- Check contention on session pool: many threads waiting on Mutex?

**Optimization Strategies:**
- Reduce lock contention by using sharded SessionPool (multiple mutexes) or `parking_lot::Mutex`
- Tune dynamic batch wait_ms to balance latency and batch size
- Pre-allocate output tensors to avoid reallocation per batch
- Use `Session::run` with pre-allocated input/output arrays (avoid HashMaps)
- Consider moving from crossbeam channels to rayon join/scope for lower overhead
</context>
